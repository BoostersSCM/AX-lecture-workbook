# 업무를 연결하는 AI

사내 도구와 데이터를 연결해 반복 업무를 줄이는 4주

부스터스 AX 사내 강의 · 4회 × 90분 · 전사 크루 대상(비개발)

---

## 1. 이 강의가 푸는 문제

AI 도구는 이미 다들 쓰고 있다. 그런데 **내 업무에 붙이는 순간** 대부분 여기서 멈춘다.

멈추는 이유는 프롬프트를 못 써서가 아니다. **AI가 우리 회사 데이터를 못 보기 때문**이다.
지금 대부분의 크루는 이렇게 쓰고 있다.

> 노션 열기 → 드래그 → 복사 → AI에 붙여넣기 → 결과 복사 → 다시 노션에 붙여넣기

이 방식은 세 군데서 막힌다.
1. **양** — 회의록 20건은 복붙이 불가능하다
2. **최신성** — 붙여넣는 순간 이미 과거 데이터다
3. **반복 비용** — 매주 같은 일을 매주 처음부터 한다

이 강의는 반복 복붙 중심의 업무를 연결된 작업 흐름으로 바꾼다. AI에 **커넥터**와 봇을 연결해 노션·슬랙·아사나를 직접 읽고, 확인한 결과를 페이지·채널·프로젝트에 보낸다. 최종 학습 기록은 Supabase에 저장해 다음 회차에 다시 꺼내 쓴다.

## 2. 관통 원리 — 긁·정·만·보

4회차 내내 반복되는 뼈대는 하나다. 매 회차 이 4단계 중 한 칸씩 깊게 판다.

| 단계 | 이름 | 하는 일 | 담당 회차 |
|---|---|---|---|
| 1 | **긁기** (Collect) | 흩어진 원본을 AI가 직접 읽게 한다 | 1회차 |
| 2 | **정하기** (Structure) | 읽은 것을 정해진 형식(표·DB)에 넣는다 | 2회차 |
| 3 | **만들기** (Generate) | 형식이 잡힌 데이터로 결과물을 만든다 | 1·3회차 |
| 4 | **보내기** (Deliver) | 사람이 볼 곳(슬랙·문서)까지 배달한다 | 3회차 |

> **강의 중 반복할 한 문장**
> "AI가 못 하는 게 아니라, 우리가 **어디서 긁어서 어떤 형식으로 어디로 보낼지**를 안 정해준 것이다."

## 3. 왜 '노말한 방법'인가 — 자동화의 스펙트럼

강사(도기웅)는 같은 일을 이미 시스템으로 구현해봤다. 1회차 도입에서 이 대조를 보여주고 시작한다.

| 업무 | SCM Portal에서 한 방식 | 이 강의에서 할 방식 | 해당 회차 |
|---|---|---|---|
| 부자재 이력 관리 | Next.js + DB 테이블 + 노션 자동 생성 API | 노션 DB에 AI가 직접 등재 | 2회차 |
| 사내봇 연결 | 서버 API + 권한 확인 + 목적지별 변환 | Asana 프로젝트·Notion 페이지·Slack 채널 연결 | 3회차 |
| 메일 첨부 처리 | Gmail 애드온 개발 | 수신함 자동 분류 루틴 | 4회차 |
| 업무 원본 요약 | 문서 수집 도구 + API 연동 | 노션·슬랙 원본 → 근거 포함 업무 맥락 요약 | 1회차 |

**핵심 메시지**: 시스템 개발은 규모·신뢰성·권한 통제가 필요할 때 한다. 개발에 6개월이 든다.
반면 오늘 배울 방식은 **90분에 만들고, 안 맞으면 버린다**. 대부분의 업무는 후자로 충분하다.

> 판단 기준 한 줄: **매일 100명이 쓰면 시스템, 매주 나 혼자 쓰면 커넥터.**

|---|---|---|---|

## 5. 매 회차 공통 90분 타임테이블

| 시간 | 블록 | 내용 |
|---|---|---|
| 0–10 | 체크인 | 지난주 적용 사례 1~2명 공유 (1회차는 자기소개 대신 "내가 제일 자주 하는 반복 업무") |
| 10–25 | 개념 | 슬라이드 최소. 화이트보드에 긁·정·만·보 그리기 |
| 25–40 | 라이브 데모 | 강사가 실제로 실행. **실패도 그대로 보여준다** |
| 40–75 | 실습 | 각자 실행. 강사 + 조교 1명이 순회 |
| 75–90 | 공유·정리 | 완성물 2~3개 화면 공유, 숙제 안내 |

**운영 원칙**
- 실습 시간이 전체의 40% 미만이면 그 회차는 실패다. 개념 설명이 길어지면 잘라낸다.
- 데모에서 AI가 엉뚱한 답을 내면 **고치지 말고 그대로 보여준 뒤** 왜 그랬는지 같이 진단한다. 이게 가장 기억에 남는다.
- 매 회차 슬랙 `#부스터스-AX`(가칭)에 완성물 스레드를 열고 각자 결과를 올린다.

## 6. 1회차 — AI에게 업무 원본을 읽히는 날

**주제**: 커넥터로 업무 원본을 직접 읽게 하고, 출처가 남는 업무 맥락 요약을 만든다.
**핵심 전환**: AI에게 바로 결과물을 시키지 않는다. 먼저 **무엇을 읽을 수 있고, 무엇을 읽지 말아야 하는지**를 확인한다.

**비유**: 커넥터는 회사 전체 열쇠가 아니라, 내 권한으로 열 수 있는 업무 자료실의 문만 함께 여는 **읽기 권한 카드**다.

### 개념 (10–25분)
- 커넥터란: AI가 내 권한 범위 안의 노션·슬랙·아사나 원본을 직접 읽게 하는 연결
- 복붙 방식 vs 커넥터 방식: 양이 아니라 **최신성·출처·반복 가능성**의 차이
- 읽기와 쓰기를 분리하는 이유: 원본 도구에는 먼저 쓰지 않고, 가져온 결과를 워크북에 저장한 뒤 3회차부터 확인 후 외부 도구에 전송한다
- 안전 규칙: 민감정보 제외, 접근 범위 확인, 원본에 없는 값은 빈칸, 결과 발행 전 사람 확인

### 라이브 데모 (25–40분)
1. 수강생이 지정한 Notion·Asana·Slack 원본에서 접근 가능한 범위 확인
2. 원본 1건을 읽고 제목·목적·결정사항·열린 질문으로 요약
3. 각 요약 문장 옆에 근거 문장을 붙이기
4. **일부러 범위를 벗어난 요청**: 접근할 수 없는 자료를 요청하고, 권한 범위 때문에 멈추는 장면 확인

### 실습 (40–75분) — 업무 원본 읽기

1. **원본 찾기** — 읽을 수 있는 페이지·채널·폴더와 읽지 않을 범위를 목록으로 만든다.
2. **맥락 요약** — 목적·핵심 내용·이미 정해진 일·아직 정해지지 않은 일을 나눈다.
3. **근거 확인** — 핵심 내용마다 원문 문장을 붙이고, 확인할 수 없는 값은 빈칸으로 남긴다.
4. **다음 연결 고르기** — 이 원본이 2회차에서 어떤 한 행이 될지 한 문장으로 적는다.

### 정리 (75–90분)
- 오늘의 완성물: **원본 목록 + 업무 맥락 요약 1개 + 근거 문장**
- 숙제: AI에게 읽히면 도움이 될 업무 원본 1개와, 줄이고 싶은 반복 작업 1개를 적어온다.
- 다음 회차 예고: 오늘 읽은 원본에서 액션아이템을 뽑아 Supabase·Notion DB의 한 행으로 만든다.

## 7. 2회차 — 흩어진 기록에 구조를 더하는 날

**주제**: 회의록에서 액션아이템을 뽑아 검수하고, 최종 표를 워크북 Supabase에 저장한다
**핵심 전환**: 원본을 읽는 것에서 끝내지 않고 **검토 가능한 데이터 구조로 저장하고 다시 읽는다**. 외부 업무 도구에 쓰는 일은 3회차부터 미리보기와 확인 후 진행한다.

### Supabase 미니랩 — 이 워크북이 저장되는 방식

이 워크북 자체를 실제 사례로 사용한다. 참가자가 입력한 답변은 화면에만 남지 않는다.

| 구조 | 역할 | 수강생이 이해할 질문 |
|---|---|---|
| `profiles` | 로그인한 사람의 이름·이메일·팀·역할 | 이 데이터는 **누구의 것인가?** |
| `entries` | `user_id + item_key + value`로 입력 한 건을 저장 | 반복해서 쌓이고 다시 꺼낼 **한 행**은 무엇인가? |
| `RLS` | 본인은 읽기·쓰기, 강사는 읽기만 허용 | 이 연결을 **누가 볼 수 있는가?** |

먼저 자기 워크북의 `s1.checkin` 같은 입력을 `entries`의 한 행으로 번역해본다. 그 다음 팀 업무에서도
상담 기록 한 건, 고객 요청 한 건, 프로젝트 태스크 한 건처럼 반복해서 쌓이는 단위를 찾아본다.
이렇게 **원본 → 한 행 → 결과물**을 연결하는 것이 API와 DB를 활용하는 최소 단위다.

### 개념 (10–25분)
- **형식(스키마)을 서류양식으로 설명**: "AI에게 백지를 주면 매번 다른 걸 써온다. 빈칸이 정해진 양식을 주면 매번 같은 걸 써온다."
- 실습용 공용 DB 「내 업무(연습용)」 필드 — **부서 무관 9칸**. 전체 설계는 `04_실습용_샘플회의록.md` A절:

| 필드 | 형식 | 채우는 법 |
|---|---|---|
| 작업 이름 | 제목 | 동사로 끝맺기 ("장소 예약 확인", "견적서 요청") |
| 담당자 | 사람 | 회의록에 이름이 명시된 경우만 |
| 상태 | 시작 전 / 진행 중 / 완료 | 회의록에서 못 찾으면 **시작 전** |
| 마감일 | 날짜 | "다음 주까지" → 회의 날짜 기준으로 환산 |
| 우선순위 | 긴급 / 높음 / 보통 / 낮음 | 명시 없으면 **보통** |
| 유형 | 8종 중 선택 | 회의·업무요청·확인검토·자료작성·외부협의·일정조율·승인대기·기타 — **목록 안에서만** |
| 세부내용 | 텍스트 | 무엇을 어디까지 하는지 한 줄 |
| 근거문장 | 텍스트 | 회의록 원문 문장을 **그대로** 복사 |
| 출처 회의록 | 텍스트 | 회의록 제목 + 날짜 |

> **부서 전용 DB를 쓰지 않는 이유**
> 「업무 진행 현황(이퀄베리 팀)」에는 품명·품번·협력사처럼 SCM에서만 통하는 칸이 있다.
> 다른 본부 크루에게는 낯선 데다 접근 권한도 없다. 그래서 결과는 전원이 볼 수 있는 **워크북 Supabase `entries`**에 개인별로 저장한다.
> 실제 팀 DB는 개념 설명 끝에 **1분짜리 실사례**로만 보여준다 — "실제로 굴러가는 팀 DB는 이렇게 생겼습니다. 칸 이름만 다르지 구조는 같습니다."

- **환각 방지 장치**: "빈칸은 비워둔 채로 가져와라. 추측해서 채우지 마라." 이 한 줄이 절반을 막는다

### 라이브 데모 (25–40분)
1. 수강생이 지정한 회의록 ① 또는 선택형 샘플 읽히기
2. 액션아이템만 골라 위 양식대로 표 만들기 — **각 행에 근거 문장 함께 출력**
3. 근거 문장이 없는 행 = AI가 지어낸 행. 그 자리에서 삭제하며 보여준다
4. 회의록 ①에는 함정이 4개 심어져 있다(케이터링·굿즈는 결정된 바 없음, 의자 건은 이미 처리됨, "다음 주 화요일"은 환산 필요). 데모에서 **최소 1개는 AI가 걸린다**

### 실습 (40–75분)
> 소재는 수강생이 지정한 회의록 1~3건이다. 원본이 없거나 전원이 같은 사례를 봐야 할 때만 `04_실습용_샘플회의록.md`를 대체 자료로 사용한다.

1. **가져오기** — 회의록 원본 1~3건 읽기
2. **정하기** — 액션아이템 표 만들기 (근거 문장 필수)
3. **검수** — 근거 없는 행 삭제, 담당자·날짜 확인
4. **저장** — 최종 표와 판단 근거를 워크북 Supabase에 저장하고 다시 읽기
5. (여유 있는 사람) **자기 팀 회의록**으로 같은 작업 1회 — 못 해도 무방, 숙제로 넘긴다

### 정리 (75–90분)
- **AI에게 쓰기를 시킬 때 3원칙**
  1. **미리보기 먼저** — "저장·전송하기 전에 표로 먼저 보여줘"
  2. **한 건 먼저** — 한 건의 저장·재조회 성공을 확인한 뒤 나머지
  3. **어디에 저장되는지 확인** — 워크북 entries와 외부 업무 도구의 저장 위치를 구분하기
- **함정 대조** (이 회차의 하이라이트) — `04_실습용_샘플회의록.md` E절의 함정 8개 표를 띄우고 각자 결과와 맞춰본다.
  결과 개수는 원본의 길이와 내용에 따라 달라진다. 정답 개수를 외우지 말고, 각 행의 근거와 실행 가능성을 확인한다.
  > "개수보다 중요한 것은 이 행을 원문에서 다시 찾을 수 있는가입니다."
- 숙제: **자기 팀 회의록**으로 같은 작업 1회. 우리 팀 회의록은 형식이 달라서 어디가 막히는지 관찰해 온다

## 8. 3회차 — Asana·Notion·Slack을 실제로 연결하는 날

**주제**: 기존 봇·앱 토큰을 서버에 두고, 각자가 권한을 부여한 Asana 프로젝트·Notion 페이지·Slack 채널을 실제로 연결
**핵심 전환**: 토큰을 복사하는 것이 연동의 끝이 아니다. **대상에 초대하고, 읽고, 보내고, 받은 이벤트를 검증해야** 연결이 완성된다.

이때 2회차에서 만든 Supabase 구조는 연결 결과를 기록하는 중간 허브가 된다. 같은 원본도 Asana에서는
실행할 태스크, Notion에서는 다시 찾아볼 기록, Slack에서는 지금 읽을 메시지로 모양을 바꾼다.

**비유**: 봇은 초대받은 방에서만 일하는 **담당자**다. Asana 프로젝트·Notion 페이지·Slack 채널마다
초대와 권한을 확인해야 같은 원본을 안전하게 옮길 수 있다.

### 개념 (10–20분)

- 토큰은 열쇠이고, 프로젝트·페이지·채널 초대는 출입명부다
- 서버 환경변수와 수강생이 입력하는 대상 ID를 분리한다
- 읽기·보내기·받기의 성공 기준을 각각 응답 데이터로 확인한다
- Slack 이벤트는 서명 검증, 대상 채널 확인, 봇 자기 메시지 제외가 기본이다

### 라이브 데모 (20–40분)

운영자가 준비한 봇 토큰은 화면에 보여주지 않고, 수강생이 직접 고른 대상만 바꿔가며 시연한다.

1. **Asana** — 봇을 프로젝트 멤버로 초대하고 Project GID로 태스크 3개 읽기
2. **Notion** — 페이지의 연결 추가에서 기존 앱을 선택하고 Page ID로 제목·본문 읽기
3. **Slack 보내기** — Channel ID를 지정하고 미리보기 후 봇 메시지 발송
4. **Slack 받기** — Events API Request URL을 검증하고 테스트 메시지가 Vercel에 도착하는지 확인
5. 네 결과를 Supabase에 기록할 때 원본 ID·상태·사람 확인 지점을 함께 남기기

### 실습 (40–75분)

| 단계 | 수강생이 하는 일 | 성공 기준 |
|---|---|---|
| 1 | Asana 프로젝트에 봇 초대 → 태스크 읽기 | 태스크 3개와 Project GID 확인 |
| 2 | Notion 페이지에 앱 연결 → 내용 읽기 | 페이지 제목·본문 또는 DB 행 확인 |
| 3 | Slack 봇을 채널에 초대 → 메시지 보내기 | channel·ts 응답 확인 |
| 4 | Slack 메시지 → Vercel 웹훅 받기 | event_id·channel_id·text 확인 |
| 5 | 세 연결을 목적지별 레시피로 저장 | 다음 사람이 재실행할 수 있는 문서 1개 |

### 정리 (75–90분)

- Asana는 실행할 태스크, Notion은 다시 찾을 기록, Slack은 지금 읽을 메시지로 변환한다
- 토큰은 서버에만 두고, 워크북에는 대상 URL·ID와 결과만 남긴다
- 연결 실패 시 오류 상태 코드와 권한 문제를 기록하고, 파일·샘플 JSON으로 플랜 B를 실행한다
- 숙제: 자기 업무의 Asana·Notion·Slack 중 하나를 골라 같은 연결을 1회 재실행한다

## 9. 4회차 — 내 업무 흐름을 연결하는 날

**주제**: 개인 루틴 자동화 + 각자 업무 케이스 설계
**핵심 전환**: 강사가 준 과제가 아니라 **내 업무**로 옮긴다. 정착률이 여기서 갈린다.

**비유**: 연결 설계서는 **다시 쓰는 레시피**다. 재료·순서·검수·도착지를 적어야 다음 주에도 같은 결과를 만들 수 있다.

### 복습 (0–10분)
긁·정·만·보 3주치 복습, 완성물 셋 다시 꺼내보기

### 파트 1 — 개인 루틴 3종 (10–40분)
회사 승인 절차 없이 오늘 바로 적용 가능한 개인 단위 자동화.

| 루틴 | 하는 일 | 절약 |
|---|---|---|
| 수신함 정리 | 다운로드 폴더·카톡 받은 파일을 규칙대로 자동 분류 | 주 20분 |
| 일일 로그 | 오늘 만진 파일·받은 자료를 스캔해 하루 기록 자동 생성 | 매일 10분 |
| 주간 회고 | 일일 로그 5개를 모아 KPT 회고 초안 생성 | 주 30분 |

> 강사 실제 사례로 시연한다. "3개월째 쓰고 있고, 이제 안 쓰면 불편하다"가 가장 강한 설득이다.

### 파트 2 — 케이스 클리닉 (40–70분)
각자 **자기 업무 1개**를 가져와 설계서를 채운다. 워크시트는 `03_케이스_클리닉_워크시트.md`.

1. 개인 작성 (15분)
2. 2인 1조 상호 리뷰 (10분) — "이거 진짜 매주 하나?", "여기 사람 확인 없이 넘어가도 되나?"
3. 3명 발표 + 강사 즉석 시연 (15분)

### 파트 3 — 파일 정리까지 자동화해보기 (70–80분)

데스크톱 앱이 Downloads·카카오톡 받은 파일·프로젝트 폴더를 살펴보고, 파일명·확장자·수정일 규칙으로
정리안을 제안하게 한다. 바로 이동시키지 않고 **관찰 → Dry Run → 사람 승인 → 이동 → undo** 순서로 진행한다.

강사 데모는 실제 `downloads-organizer` 도구로 보여준다. `organize.ps1 -DryRun`으로 계획을 먼저 보고,
승인된 규칙만 이동하며, 모든 이동은 `moves.csv`에 남기고 `undo.ps1`로 되돌릴 수 있게 한다.

- 삭제 금지, 폴더와 최근 파일 보호
- 애매한 파일은 보류 목록으로 남기기
- 이동 내역은 CSV로 기록하고 `undo` 가능하게 만들기
- 반복 패턴이 확인된 규칙만 다음 실행에 승격하기

### 정리 (80–90분)
- **하면 안 되는 것** 재확인 (아래 10절)
- 사내 지원 채널 안내, 4주 뒤 '이번 달 자동화 TOP3' 공유 예고

## 10. 안전 규칙 — 매 회차 상단 고정

> 이 4줄은 매 회차 첫 슬라이드에 그대로 띄운다.

1. **긁지 않는다** — 개인 연락처, 급여·평가, 계약 단가, 미공개 재무. 내가 볼 수 있어도 AI에 넘기지 않는다
2. **쓰기 전에 본다** — AI가 노션·슬랙에 무언가 쓰기 전에 반드시 초안을 눈으로 확인한다
3. **채널 발송은 사람이 누른다** — 전사 채널·외부 메일 자동 발송 금지
4. **대상을 구분한다** — 1·2회차는 워크북에 저장하고, 3회차 외부 전송은 본인이 지정한 실습용 대상에서 미리보기·확인 후 실행한다

추가로 강의 중 명시할 것:
- 커넥터의 접근 범위 = **내 계정 권한 범위**. 권한 없는 페이지는 AI도 못 본다 (안심 포인트)
- 협력사명·단가가 섞인 자료는 요약 결과도 사내 공유 범위를 지킨다
