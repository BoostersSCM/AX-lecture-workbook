# 2회차 진행안 — 흩어진 기록에 구조를 더하는 날

**90분 · 실습 소재: 공용 샘플 회의록 3건 → 「내 업무(연습용)」 DB**

**비유로 시작하기**: DB는 메모를 쌓아두는 창고가 아니라, 다음 사람이 다시 찾을 수 있도록 칸과 라벨을 정해둔 서랍장입니다.

---

## 이 회차의 목표

**AI가 지어낸 항목을 눈으로 잡아내는 경험을 시킨다.**

1회차는 읽기만 했습니다. 오늘부터 AI가 우리 노션에 **씁니다.**
쓰기를 가르치는 회차의 진짜 내용은 "어떻게 쓰게 하는가"가 아니라 **"어떻게 검증하는가"**입니다.
그리고 이 워크북 자체를 보며 **입력 한 건이 DB의 한 행이 되는 구조**까지 이해합니다.

**끝났을 때 상태**
- 각자 「내 업무(연습용)」 DB에 항목 10개 이상 등재
- "근거문장이 없는 행 = AI가 지어낸 행"을 직접 발견해봄
- 쓰기 3원칙(미리보기 먼저 / 한 건 먼저 / 되돌릴 수 있게)을 말할 수 있음
- `profiles / entries / RLS`의 역할을 설명하고, 내 입력 하나를 `entries` 한 행으로 번역해봄

## [10–25] 개념 — 형식을 정한다는 것

### 화이트보드 실연 (이 회차 개념의 전부)

마커를 들고 **직접 그리면서** 설명합니다.

**1) 백지를 준 경우**
```
[백지]  "회의 내용 정리해줘"
   → 1주차: 줄글 요약
   → 2주차: 불릿 목록
   → 3주차: 표 (열 구성이 또 다름)
```
> "매주 다른 게 나옵니다. 쌓이지가 않습니다."

**2) 양식을 준 경우**
```
┌──────┬──────┬──────┬──────┐
│작업이름│담당자 │마감일 │ 근거 │
├──────┼──────┼──────┼──────┤
│      │      │      │      │
└──────┴──────┴──────┴──────┘
```
> "빈칸이 정해진 서류를 주면 매주 같은 게 나옵니다. **쌓이면 그게 데이터입니다.**"

### Supabase 미니랩 — 워크북 뒤의 DB (8분)

화면을 잠깐 내려놓고 실제 워크북의 저장 구조를 보여줍니다.

```text
profiles  : 로그인한 사람 — id / email / name / team / role
entries   : 입력 한 건    — user_id / item_key / value / updated_at
RLS       : 접근 규칙     — 본인은 읽기·쓰기, 강사는 읽기만
```

참가자에게 현재 본인이 적은 `s1.checkin`을 예로 들어 묻습니다.

> "이 문장이 `entries`에 들어가면 `item_key`는 무엇이고, `value`는 무엇일까요?"

핵심은 테이블을 외우는 것이 아닙니다. **반복해서 쌓이고 다시 꺼내 쓸 단위가 한 행**이라는 감각을 만드는 것입니다.
그 다음 공용 DB 9칸을 소개합니다.

`04_실습용_샘플회의록.md` A절 표를 띄웁니다. 하나하나 설명하지 말고 **세 칸만** 짚습니다.

| 칸 | 짚을 것 |
|---|---|
| **유형** (8종) | "목록 안에서만 고르라고 해야 합니다. 안 그러면 매번 새 이름을 만들어냅니다." |
| **근거문장** | "실무 DB엔 없는 칸입니다. **오늘만 쓰는 검증 장치**입니다." |
| **상태 / 우선순위** | "회의록에 없으면? → 시작 전 / 보통. **기본값을 미리 정해둡니다.**" |

### ★ 환각 방지 한 줄

> "AI는 빈칸을 보면 채우고 싶어 합니다. 그래서 이렇게 씁니다 —
> **'추측해서 채우지 마라. 모르면 빈칸으로 두라.'**
> 이 한 줄이 절반을 막습니다."

### 1분 실사례 (부서 전용 DB 보여주기)

이퀄베리 팀 실제 DB를 잠깐 띄웁니다.

> "이건 제 팀이 실제로 쓰는 겁니다. 품번, 협력사 같은 칸이 있죠. 여러분 팀은 다른 칸이 필요할 겁니다.
> **칸 이름만 다르지 구조는 똑같습니다.** 오늘은 어느 팀에서나 통하는 9칸으로 연습합니다."

## [25–40] 라이브 데모 — 지어낸 행 잡아내기

> **이 데모가 2회차의 전부입니다.** 시간이 밀려도 이건 끝까지 합니다.

### 1단계 — 나쁜 요청 먼저 (3분) ★

일부러 규칙 없이 던집니다.

```
「AX 실습장」의 샘플 회의록 3건 읽고 액션아이템 뽑아줘
```

결과가 **20개 넘게** 나옵니다. 화면에 띄운 채로 묻습니다.

> "많이 나왔죠? 좋아 보입니까?"

### 2단계 — 한 줄씩 검증 (5분)

나온 항목 중 이런 것들을 찾아 짚습니다.

- **케이터링 준비** → 회의록에는 "예산 확인해보고 다음 회의 때 다시 얘기하시죠. 아직 정해진 건 없습니다"
- **사내 굿즈 증정 준비** → "검토만 해보고, 확정은 나중에요"
- **의자 추가 확보** → 이미 지난번에 처리된 건

> "이 세 개, 회의에서 **아무도 하기로 하지 않았습니다.**
> 그런데 지금 우리 업무 목록에 들어왔습니다. 다음 주에 이게 뭐로 뜰까요? **지연**으로 뜹니다.
> 하지도 않기로 한 일이 지연으로 뜹니다."

### 3단계 — 규칙을 넣고 다시 (5분)

프롬프트 카드 2회차 2단계 전문을 붙여넣고 재실행. **13~15개**로 줄어듭니다.

> "6개가 사라졌습니다. 사라진 게 아니라 **원래 없던 겁니다.**"

### 4단계 — 근거문장 검증 (2분)

```
방금 만든 표에서, 근거문장이 회의록에 실제로 있는지 다시 확인해줘.
원문에서 못 찾은 행이 있으면 그 행만 따로 알려줘.
```

> "이게 오늘 배우는 유일한 기술입니다. **근거를 같이 내놓게 하고, 근거를 확인한다.**"

## [40–75] 실습

### 0단계 — DB 복제 (5분, 전원 동시)

> "먼저 「내 업무(연습용)」 DB를 각자 복제하세요. 우측 상단 `...` → 복제.
> **한 DB에 열두 명이 동시에 쓰면 서로 섞입니다.**"

전원이 복제를 마쳤는지 **눈으로 확인하고** 다음으로 넘어갑니다.

### 1~4단계 (30분)

| 단계 | 내용 | 시간 |
|---|---|---|
| 1 | 샘플 회의록 3건 긁기 | 3분 |
| 2 | 액션아이템 표 만들기 (프롬프트 카드 2단계) | 10분 |
| 3 | 근거문장 검증 → 이상한 행 삭제 | 7분 |
| 4 | 내 복제 DB에 등재 (1건 먼저 → 나머지) | 10분 |

### 순회 체크포인트

**5분차** — 복제를 안 한 사람이 있는지. 반드시 전원 확인.
**20분차** — 표가 나왔는지. 항목 수를 물어봅니다. **20개 넘으면 규칙이 빠진 겁니다.**
**30분차** — 등재 전에 "미리보기 먼저 요청했는지" 확인.

### 자주 막히는 지점과 대응

| 증상 | 원인 | 대응 |
|---|---|---|
| 항목이 20개 넘음 | "논의만 된 건 제외" 규칙 누락 | 프롬프트 카드 2단계의 **규칙 2**를 다시 붙여넣게 함 |
| 항목이 8개 미만 | 회의록을 1건만 읽음 | 3건 다 읽었는지 확인 |
| 마감일이 "다음 주" 그대로 | 환산 지시 누락 | "회의 날짜 기준으로 실제 날짜로 환산해줘" 추가 |
| 담당자에 아무나 들어감 | 명시된 경우만 규칙 누락 | 회의록 원문과 대조시킴. **좋은 학습 순간** |
| 유형에 없는 값이 생김 | 목록 제한 누락 | "이 8개 중에서만" 다시 강조 |
| 등재가 안 됨 | 복제 DB 이름이 원본과 같아 헷갈림 | 복제본 이름을 `내 업무(연습용)_홍길동`으로 바꾸게 함 |
| 한 번에 15건을 등재해버림 | 미리보기 건너뜀 | 되돌리는 법 시연 — 비고의 `AX실습-날짜` 표시로 필터해서 삭제 |

## [75–90] 정리

### ★ 함정 대조 (8분) — 이 회차의 하이라이트

`04_실습용_샘플회의록.md` E절 함정 표를 띄웁니다. 항목별로 "이거 걸린 사람?" 하고 손을 들게 합니다.

| # | 함정 | 대체로 몇 명이 걸리나 |
|---|---|---|
| 3 | 논의만 된 것을 액션으로 | **대부분** |
| 2 | 상대 날짜 미환산 | 절반 |
| 1 | 담당자 임의 배정 | 절반 |
| 6 | 초안과 최종을 한 건으로 합침 | 소수 |

> "많이 걸리셨죠. 여러분이 못한 게 아니라 **원래 걸리게 만들어 놓은 회의록**입니다.
> 실제 회의록은 이보다 더 지저분합니다."

### 쓰기 3원칙 (5분)

화이트보드에 크게 씁니다.

1. **미리보기 먼저** — "등재하기 전에 표로 보여줘"
2. **한 건 먼저** — 1건 확인하고 나머지
3. **되돌릴 수 있게** — 복제본에서, 표시를 남기고

### 마무리 멘트 (2분)

> "오늘 만든 이 DB, 지우지 마세요. **다음 주 재료입니다.**
> 3회차에는 이 데이터를 Asana 프로젝트·Notion 페이지·Slack 채널로 실제 연결합니다."

### 숙제

> **자기 팀 회의록**으로 오늘과 같은 작업 1회.
> 잘 되는지가 아니라 **어디서 막히는지**를 보고 오세요. 우리 팀 회의록은 형식이 달라서 분명히 막힙니다.
> 막힌 지점을 슬랙 스레드에 한 줄 적어주세요 — 3회차 시작할 때 같이 봅니다.

## 시간 조절

**뒤처질 때 자르는 순서**
1. 실습 4단계(등재)를 3건만 하고 나머지는 숙제
2. 1분 실사례
3. 함정 대조를 8개 → 상위 3개만

**절대 자르지 말 것**: 데모 1~3단계(나쁜 요청 → 검증 → 규칙 넣고 재실행), DB 복제 확인

**시간이 남을 때**
- 회의록 ③(계정·권한 정비)만 따로 다시 돌려서, 함정 #8(검토도 액션인가) 토론
- "우리 팀이라면 이 9칸에서 뭘 더 넣고 뭘 뺄까" 조별 토론

## 이 회차가 실패하는 경우

| 신호 | 의미 | 조치 |
|---|---|---|
| 함정 대조에서 손 드는 사람이 거의 없음 | 실습을 안 했거나 대충 함 | 3회차 연결 실습을 2인 1조로 |
| 등재 단계까지 간 사람이 절반 미만 | 시간 배분 실패 | 3회차는 연결 대상 ID와 봇 초대부터 확인하도록 준비 |
| "이거 우리 팀에서 못 쓸 것 같다" 반응 | 공용 소재의 한계 | 4회차 케이스 클리닉에서 개별 대응. 숙제 피드백을 반드시 챙길 것 |
